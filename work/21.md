# 21 — feat(foundations): derive accent vars via color-mix

## 2026-05-10 — Initial development

### Summary
Cinq variables d'accent dérivées ajoutées à `tokens.css`. Toutes calculées via `color-mix()` à partir de `var(--accent)` et des anchors neutres (`--bg-app`, `--fg-primary`), donc :
- changent automatiquement à chaque navigation entre pages (suivent `--accent`)
- s'adaptent à light/dark sans logique supplémentaire (les anchors swappent)
- animent en même temps que `--accent` grâce aux `@property` ajoutés

### Choix d'espace : `in oklch`
Toutes les `color-mix()` utilisent `in oklch`. Raison : interpolation perceptuellement uniforme — pas de zone grise/désaturée au milieu du mix, contrairement à `in srgb` qui peut produire des « tunnels » ternes quand on mélange des teintes très saturées. C'est notamment visible quand on mix `--accent` (saturé) avec `--bg-app` (cream/anthracite) sur 12% — `in oklch` donne un pastel propre, `in srgb` donne du beigeasse.

### Formules
```css
--accent-bg:        color-mix(in oklch, var(--accent) 12%, var(--bg-app));
--accent-bg-hover:  color-mix(in oklch, var(--accent) 18%, var(--bg-app));
--accent-fg:        var(--accent);                                          /* alias sémantique */
--accent-fg-on-bg:  color-mix(in oklch, var(--accent) 80%, var(--fg-primary));
--accent-border:    color-mix(in oklch, var(--accent) 40%, transparent);
```

### Decisions
- **`--accent-fg`** est un alias direct de `--accent`. Donné par la spec §2.4 (« accent à 100% »). Le nom existe pour que les composants aient une variable sémantique pour le foreground accentué, sans avoir à connaître `--accent` directement.
- **`--accent-fg-on-bg`** : mix 80% accent + 20% `--fg-primary`. En light mode `--fg-primary` est très foncé (`#1f1b14`), donc le mix darkens l'accent → meilleur contraste contre `--accent-bg` (clair). En dark mode `--fg-primary` est off-white (`#f2efe6`), donc le mix lightens l'accent → contraste contre `--accent-bg` (foncé). Formule symétrique qui marche dans les deux modes sans branchement.
- **`--accent-border`** : 40% accent sur transparent. Donne une bordure visible mais subtile qui hérite du hue de la page. Sur `--bg-app` directement (cream/dark), le rendu est correct ; si la bordure est posée sur `--accent-bg`, elle se confond — c'est OK, on n'aura jamais de border accent sur surface accent.
- **`@property` pour les 5 vars dérivées** : nécessaire pour que `color-mix()` interpole quand `--accent` change. Sans `@property`, les valeurs sont traitées comme des strings et snap au lieu d'animer. Avec `syntax: '<color>'`, le browser recompute le mix à chaque frame de la transition.

### AA — limites de la vérification CSS pure
Le critère « AA ≥ 4.5:1 » sur `--accent-fg-on-bg` ne peut pas être *prouvé* en pur CSS — il n'y a pas de fonction `contrast()` dans CSS. La formule choisie (80/20) déplace systématiquement la teinte vers le `fg-primary`, ce qui améliore le contraste mais ne le garantit pas pour toutes les teintes.

**Vérification manuelle nécessaire** :
- Light mode : 6 hues × `--accent-fg-on-bg` sur `--accent-bg` → mesurer ratio contraste (Chrome DevTools → Inspect → Color picker → Contrast ratio).
- Dark mode : idem.
- Si une teinte échoue (probable candidat : skill vert pâle dark), envisager :
  - augmenter le mix vers fg-primary (90/10 au lieu de 80/20),
  - ou créer un fallback par-page via `[data-page='skill'] { --accent-fg-on-bg: var(--fg-primary); }`,
  - ou rendre `--accent-fg-on-bg` = `var(--fg-primary)` tout court (simple mais perd la couleur d'identité).

Ce point est documenté pour un check visuel au moment où le premier composant utilise `--accent-fg-on-bg` (probablement #7 ExperienceCard).
