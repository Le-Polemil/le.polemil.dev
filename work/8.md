### Key decisions

- **Sub-routes (`/code`, `/props`) plutôt que `?tab=code`** : l'AC dit "query param OU nanostore" — j'ai choisi sub-routes pour 3 raisons : (1) idiomatique Astro (pas besoin d'adapter SSR), (2) View Transition d'Astro fonctionne automatiquement entre routes via ClientRouter (AC "Switch onglet : View Transition fluide"), (3) SEO-friendly (chaque tab a son URL canonique). Déviation documentée ici.
- **TabBar comme primitive `.astro`** : pas interactif côté state (chaque tab est un `<a>` qui change d'URL). L'actif est déterminé par la page courante côté serveur. Aucun JS shipped pour les tabs eux-mêmes.
- **`role="tab"` + `aria-selected`** sur les anchors : usage non-standard (tabs sont normalement des `<button>` dans le pattern WAI-ARIA Tabs), mais ici les "tabs" sont en réalité de la navigation (pas du show/hide local). Choix pragmatique pour combiner sémantique tab + SEO/sharable URLs.
- **CodeBlock sans syntax highlighting** : phase 1 = plain mono. Shiki/Prism viendront plus tard si besoin. Le ticket ne mentionne pas le highlighting.
- **Props table en `<table>` sémantique** plutôt qu'en flex/grid de divs : `<th>` + `<td>` donnent la sémantique native aux screen readers. Style via CSS reset + token-bound.
- **`ComponentDocHeader.astro` shared** : factorise l'eyebrow + h1 + subtitle + TabBar entre les 3 pages. Pas une primitive (specific to component docs) — vit dans `system/`.
- **`ExperiencePreview` dans `src/patterns/`** : conforme à l'architecture doc (§2 layout `patterns/Timeline.astro`, `ExperiencePreview.astro`, `Changelog.astro`).
- **Pas de variant-pills sub-selector** : le Figma montre une rangée "default / expanded / compact / timeline" sous le contenu des tabs Code et Props (sélecteur pour switcher quelle variant est documentée). L'AC ne le demande pas, et ça ajouterait un state UI significatif. **Hors scope #8, à traiter dans un futur ticket UX si besoin.**

### Déviation acceptée : sub-routes vs `?tab=`
L'AC dit "query param `?tab=code` OU state nanostore". Le dev a livré une **3e option** (sub-routes). Strictement parlant, ce n'est ni l'une ni l'autre. Cependant :
- L'**intention** est satisfaite : URL persiste l'état d'onglet (par la pathname au lieu du query string).
- View Transition gagné gratuitement (ClientRouter Astro), critère que `?tab=` n'aurait PAS donné facilement (le query change ne déclenche pas un navigate, juste un replaceState).
- SEO + partage de lien meilleurs avec sub-routes.

Si tu tenais à `?tab=` (e.g., pour une intégration future avec un store de tab), il faudra refactor. **Pas bloquant pour ce ticket**. Confirme ou demande le refactor.

### 🟡 Important (non bloquant)
- **`role="tab"` + `aria-selected` sur des `<a>`** : non-standard. La pattern WAI-ARIA "Tabs" suppose `<button>` + `aria-controls` pointant vers un tabpanel local au DOM. Ici les onglets sont en réalité de la navigation entre pages — le bon pattern aurait été `<nav role="navigation">` + `<a>` + `aria-current="page"` sur l'actif. La sémantique actuelle marche en pratique (screen readers vont annoncer "Code, sélectionné" et le link est cliquable), mais ce n'est pas la pattern canonique. **Refactor possible** : drop `role=tablist`/`role=tab`/`aria-selected`, add `aria-current="page"` sur l'actif. Le visuel reste identique.
